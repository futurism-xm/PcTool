# 长截图滚轮与拼接优化验证（2026-10-13）

本次范围为长截图的输入调度、图像匹配和成图；保留工作区原有修改，未修改公开接口、保存格式或用户设置。项目使用 C++17、Win32、CMake/Ninja、MSVC。长截图数据流为鼠标钩子 → 界面调度 → 来源窗口滚动 → Desktop Duplication 采集 → 稳定帧匹配 → 预览／分条带结果 → 最终图像。

## 发现与修复

| 严重程度 | 位置及触发条件 | 影响与依据 | 处理 |
|---|---|---|---|
| P2，已确认 | `long_capture_session.cpp` 原调度同时要求投递间隔 350ms、待办输入有效期 150ms；首滚后约 100ms 再输入 | 第二次输入在等待自身处理期间过期，停手后不再执行。旧版真实桌面回归明确失败：`Input received while waiting was lost` | 使用最新意图单槽，取消等待过期；真实动作成功匹配后允许立即交接。完成状态绑定动作，失败／取消不能放行 |
| 已测量的计算瓶颈 | `scroll_stitcher.cpp:MatchVerticalBands` 在每个位移候选中重复计算相同像素的灰度、纹理和原位差值 | 原版 4K 追加匹配中位 478.230ms | 按窄列带缓存精确整数值、复用缓冲；位移范围、累加顺序、置信度和歧义判定不变 |
| 已测量的冗余计算 | 首次锁定计算不会使用的正文背景列；成图／预览对每个像素重复寻找条带 | 原版 4K 最终成图中位 56.027ms | 仅计算两侧背景、复用中位数缓冲；每行定位一次条带、连续复制，并预计算预览横向采样 |

调度仍保留初帧准备、200ms 画面稳定确认、整格控件 350ms 后补足 120 单位、原有边界确认、步长限制、来源检查与 Chromium 投递方式。手动输入优先于自动续滚；暂停／结束／取消同时使界面待办和钩子通知失效。已补充虚拟时钟及真实桌面回归，验证最新方向覆盖、单一在途动作、有限尾部、旧通知不重放、失败后新输入重试。

## CPU 拼接对照

同机 AMD Ryzen 7 5800H、Windows x64、MSVC Release `/O2`。同一进程内交替调用旧／新算法，三轮；每轮预热 3 对、正式 30 对，每项各 90 个样本。输入生成、状态复制和正确性校验不计入耗时；测量期间未运行项目构建或其他测试。此 CPU 工具的中位数取两个中央样本中的较大者，P95 使用 nearest-rank；两版使用相同口径。

## 桌面端到端测量

使用独立 900×740 原生测试窗口，正文 900×660；真实 SendInput、来源绘制、采集、匹配及预览 WM_PAINT 全链路打点。场景为即时、平滑、250ms 延迟、整格控件及自动滚动。每次首动单列，随后 3 次预热、30 次正式动作；新旧版本交替三轮。每轮检查动作数、方向、位移、新增高度相同，并校验最终像素。

测试专用 `PCTOOL_SCROLL_TRACE` 在生产构建中完全移除。回访不生成新图像，因此预览与绘制统计仅纳入真实重绘；自动续滚没有逐动作物理输入，采用投递起算。原始捕获统计另含准备、等待和边界阶段，不能当作同样数量的滚动动作样本。端到端中位数取两个中央值的平均，P95 使用 nearest-rank；吞吐以每轮第一个正式动作投递至最后一个正式动作发布的窗口计算，含回访、排除准备和最终边界等待。

## 限制与剩余疑点

- 第一次旧版 Electron 运行曾出现首滚 `moves=1`，输入保护断言失败；加入鼠标阶段和 DOM 事件记录后，旧版复跑及新版普通／大步首滚均通过，未放宽断言。该偶发问题的原因尚未证实，不能宣称已修复；保留事件日志供再次复现时定位。
- 端到端测试是当前桌面上的合成原生窗口；Electron 用独立合成页面，不代表所有浏览器页面或第三方应用。4K 对照为 CPU 图像算法测试，未将其提速比例直接用于真实 4K 桌面体验。
- 来源动画、响应延迟、稳定确认和显示刷新仍影响操作速度；没有取消稳定确认来换取表面上的低延迟。
